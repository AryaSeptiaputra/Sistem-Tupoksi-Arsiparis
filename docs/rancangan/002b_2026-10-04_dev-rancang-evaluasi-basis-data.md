# 002b · Dev · Rancang evaluasi basis data

Status: disetujui 2026-10-04
Dari: docs/rancangan/002a_2026-10-04_dev-rancang-evaluasi-basis-data.md
Kondisi kode: Flask 3.1 + SQLAlchemy 2.0 murni (tanpa Flask-SQLAlchemy), MySQL lewat PyMySQL, skema lama 12 tabel dibuat dengan `create_all` saat `create_app()` (`app/__init__.py:80`), belum ada Alembic. Logika lama yang menjadi pembanding baseline: `app/services/disposal.py:14` `get_expired_archives(db)` (memakai `datetime.now()` di dalam fungsi) dan `app/services/retention_scheduler.py:14` `check_and_deactivate_archives()` (membuka session sendiri lalu commit). Belum ada alat evaluasi, folder `data/`, atau `outputs/`. Test yang ada (`tests/test_app.py`, `tests/test_pagination.py`) memakai engine dari `.env`, dan `tests/test_pagination.py:30` memanggil `drop_all`. Di root ada script `test_*.py` ad-hoc (tidak di-track git) yang ikut terkumpul kalau `pytest` dijalankan tanpa path. `.venv` memakai Python 3.10.11, sedangkan Docker dan CI memakai 3.11. Kode lama tidak diubah di rencana ini.

Letak alat: paket `evaluation/` di root, terpisah dari `app/`. Alasannya, B2/B3 harus meng-import kode lama `app/`, sementara alat ini tidak boleh ikut ke image produksi. Titik masuk ada di `scripts/evaluation/`, test ada di `tests/evaluation/` (susunannya mengikuti `evaluation/`).

## Tidak dibangun di rencana ini
- Skema baru, Alembic 0001, model ORM, ETL, fungsi domain transisi/retensi, dan scheduler baru. Semuanya rancangan 001 → 001b.
- Label golden D2/D3, ±10 baris anomali, dump dan restore D1. Semuanya dikerjakan Arya.
- Menjalankan baseline atau evaluasi di DB MySQL sungguhan. Perintahnya ditulis di laporan; dijalankan Arya, atau pink-chan kalau diminta eksplisit.
- Perbaikan test lama (`tests/test_pagination.py` drop_all, `tests/test_app.py`) dan script `test_*.py` ad-hoc di root, karena di luar cakupan 002a (lihat Risiko 1).
- Pengukuran Dev-B. Alatnya sama, cukup dijalankan dengan `--sumber nyata` saat data nyata ada.
- Target kinerja. B6 dan Waktu_jalan hanya informasi.

## Risiko teknis
1. **Test lama bisa menyentuh DB dari `.env`.** `tests/test_pagination.py:30` memanggil `Base.metadata.drop_all` ke engine dari `.env`, dan `pytest` tanpa path ikut mengumpulkan script ad-hoc di root. Penanganan: test alat ini hanya dijalankan dengan `pytest tests/evaluation`. `tests/evaluation/conftest.py` memasang `DATABASE_URL` palsu yang tidak bisa dihubungi sebelum `app` di-import, dan menolak engine selain SQLite sementara. Perbaikan test lama disarankan sebagai perintah terpisah.
2. **Import kode lama ada efek sampingnya.** `import app...` membaca `.env` lewat `Settings()` dan membuat engine aplikasi. `LegacyCodeRunner` meng-import secara lambat, setelah memasang `DATABASE_URL` = URL D1. `create_app()` tidak pernah dipanggil, karena fungsi itu menjalankan `create_all` dan menyalakan APScheduler.
3. **B3 memakai fungsi lama yang melakukan commit.** Pengganti `SessionLocal` mencatat `session.dirty` saat `commit()` dipanggil, lalu rollback. Koneksi D1 juga dibuat READ ONLY, jadi kalau kode lama sempat flush, hasilnya error, bukan penulisan diam-diam. Disarankan juga memakai user MySQL yang hanya punya hak SELECT untuk D1.
4. **Kode lama memakai `datetime.now()` di dalam fungsi.** Untuk B2/B3, `datetime` di modul lama dipatok ke `tanggal_uji` (pukul 00:01, sama dengan jadwal scheduler). Kode lama tidak diubah (E2). Kalau |L| = 0 di dummy (E5), baseline dijalankan sekali lagi dengan `tanggal_uji` yang dimajukan, khusus untuk ekuivalensi.
5. **Perbedaan B2 dengan route.** B2/B6 memanggil fungsi service lama, bukan endpoint HTTP, jadi tanpa JWT dan jsonify. Isi L sama dengan `/disposal/check`. Waktu B6 tidak memuat overhead HTTP dan bergantung mesin, jadi hanya informasi.
6. **Pemeriksaan M1 bisa berputar pada dirinya sendiri.** Kalau Alembic/ORM 001b dibangkitkan dari `evaluation/spec`, M1 hanya membandingkan spesifikasi dengan dirinya sendiri. Aturan untuk 001b: Alembic dan model ORM ditulis dari 001a dan tidak meng-import `evaluation/spec`.
7. **Nama CHECK hanya sebagian ditetapkan 001a.** 001a hanya menyebut 4 nama CHECK disposal dan `ck_archive_destroyed_file`. CHECK domain lain di spesifikasi diberi nama `ck_<tabel>_<kolom>` (contoh `ck_archive_status`) mengikuti naming convention K6. 001b wajib memakai nama yang sama, kalau tidak M1 akan melaporkannya di E \ A.
8. **Kasus negatif M1 menggeser AUTO_INCREMENT**, walaupun di-rollback. Karena itu M1 dijalankan setelah ETL (urutan E2E), dan Idempotensi M2 membandingkan dua DB kosong yang terpisah (`EVAL_NEW_DB_URL`, `EVAL_NEW_DB_URL_2`).
9. **Kontrak dengan 001b.** Nama persisnya ditetapkan di 001b dan evaluator memanggilnya lewat satu adapter:
   - fungsi retensi per kasus `(arsip, klasifikasi, status, disposal_terbuka, tanggal_uji) → (jatuh_inaktif, daftar)`;
   - scheduler yang menerima session/engine dan `today: date`, mengembalikan jumlah baris diubah;
   - fungsi transisi arsip dan disposal yang menolak transisi tidak sah dengan error milik project;
   - peta id lama → baru dari ETL yang bisa dibaca sebagai berkas;
   - perintah ETL ke DB kosong dengan tanggal ETL sebagai parameter.
   Kalau 001b tidak bisa memenuhi salah satunya, langkah 7–10 disesuaikan sebagai perubahan kecil dan dicatat di laporan.
10. **Versi Python.** `.venv` 3.10.11, Docker/CI 3.11, sedangkan writer-code meminta 3.12+. Kode alat ditulis kompatibel 3.10. Satu-satunya dependency baru adalah openpyxl (pilihan Arya: .xlsx); SQLAlchemy, PyMySQL, pydantic-settings, dan pytest sudah terpasang. Format log hanya `text`, karena `python-json-logger` belum terpasang dan alat ini dipakai di terminal.
11. **MySQL D1 belum diketahui versinya (E1).** CHECK butuh ≥ 8.0.16. M1 melaporkan versi server lebih dulu, dan pola "Penolakan < 100% hanya CHECK" di tabel Membaca hasil langsung terbaca.
12. **`data/` dan `outputs/` di-gitignore (aturan writer-code)**, jadi `golden_*.jsonl` tidak ikut git. Spreadsheet sumber Arya tetap menjadi salinan induknya.
13. **Folder `<tanggal>` di `outputs/evaluation/` adalah tanggal jalan.** `tanggal_uji`, sumber, dan URL DB tanpa kata sandi dicatat di `meta.json` tiap putaran.
14. **openpyxl dan berkas requirements.** openpyxl hanya dipakai alat evaluasi, tidak oleh aplikasi, jadi tidak masuk `requirements.txt` produksi (yang juga ber-encoding UTF-16 LE + BOM, CRLF; tidak disentuh supaya tidak ada perubahan encoding tak sengaja). Dibuat `requirements-dev.txt` baru (UTF-8) yang diawali `-r requirements.txt` sesuai writer-code 2.9; pip membaca BOM UTF-16 di berkas yang dirujuk. Versi openpyxl dan dependency-nya (`et-xmlfile`) dikunci `==` di langkah 5 dengan versi yang benar-benar terpasang di `.venv` (Python 3.10). openpyxl tidak bentrok dengan dependency produksi, jadi tidak perlu `requirements-eval.txt` terpisah. Memindahkan pytest/pytest-cov/coverage dari `requirements.txt` ke `requirements-dev.txt` di luar cakupan 002b. Workbook dibaca `read_only=True, data_only=True`; sel berisi rumus terbaca sebagai nilai tersimpan terakhir, jadi Arya menyimpan workbook dari Excel sebelum konversi.

## Koreksi selama putaran
- Arya memilih format spreadsheet .xlsx, bukan usulan CSV. Akibatnya: pembaca workbook `evaluation/golden/workbook.py` (openpyxl), kerangka D3 dari pemilih juga .xlsx, dan dependency openpyxl masuk langkah 5 (Risiko 14).
- Arya memilih aturan `diverifikasi` usulan: wajib di baris `uji_akhir` (ditolak bila kosong); baris `perbaikan` yang kosong hanya diberi peringatan.
