# 003b · Dev · Rancang evaluasi data seed Dev-A

Status: disetujui 2026-10-06
Dari: docs/rancangan/003a_2026-10-05_dev-rancang-evaluasi-data-seed.md
Kondisi kode: alat evaluasi 002b langkah 1–3 sudah ada di `evaluation/` (`config.py`, `db.py`, `report.py`, `factory.py`, `baseline/` B1–B6) beserta titik masuk `scripts/evaluation/run_baseline.py`. Test di `tests/evaluation/` memakai SQLite sementara, dengan fixture `old_db` (skema lama dari `app/models` + anomali B4). Belum ada fungsi hash baris (M2 baru dibangun di 002b langkah 7). `scripts/evaluation/b4_anomali_template.sql` dan `b4_anomali_dev_a.sql` ada, tetapi belum pernah dijalankan di D1. Skema lama dibuat `create_all` dari `app/models`. Subfolder lampiran lama per route: `incoming_letters`, `outgoing_letters`, `diplomas`, `finance_archives`, `employee_archives` (`app/utils/file_helper.py:88` menyimpan `storage/documents/<subfolder>/<nama>`). Kolom `diploma` tidak punya `archive_status`. D1 `tupoksi_d1` berisi 1 akun, 1 pegawai, 203 log, 35 master_reference, 0 klasifikasi, dan 0 arsip. Arya memakai Windows cmd dengan `.venv` Python 3.13; user `eval_ro` di D1 hanya punya hak SELECT.

Letak: paket `evaluation/seed/`, karena seed adalah alat evaluasi, bukan bagian aplikasi (003a; ikut `.dockerignore` `evaluation/`). Titik masuk di `scripts/evaluation/`, test di `tests/evaluation/`. Seed menulis lewat SQLAlchemy Core ke tabel hasil reflect dari D1. Seed tidak meng-import model ORM lama, sehingga yang ditulis mengikuti skema D1 yang sebenarnya.

## Risiko teknis
1. **SY4 dan cara hitung B4.** `run_baseline` menghitung B4 per baris temuan. Dengan isi DS6 (B4-1 sepasang nomor ganda; B4-2 tiga sub-butir: archive_status, final_action, approval_status), keluarannya `2/3/1/1/1/1/1`, bukan "tepat 1 per butir". Usulan: pemeriksa SY4 memakai target `2/3/1/1/1/1/1` (satu kasus per butir atau sub-butir) dengan `--anomali`, dan `0` tanpa `--anomali` (Pertanyaan 1).
2. **Penanda baris anomali vs SY8/SY9.** DS6 mempertahankan penanda `ANOMALI-`, dan baris induk lama di SQL (`ANOMALI-INDUK pegawai`, identity `ANOMALI-B4-4`) bukan "Dummy" dan tidak berawalan 9900. Akibatnya SY9 gagal, dan SY8 (baris berpenanda = baris ditambahkan) tidak terpenuhi kalau penandanya hanya DUMMY. Usulan: kolom penanda baris anomali memakai format DS7 ditambah tag `ANOMALI-B4-n` (misalnya nama pegawai berformat "Pegawai Dummy" + tag, identity 9900…); nilai pelanggar B4 tetap persis seperti `b4_anomali_dev_a.sql`; induk memakai klasifikasi seed `DMY-P55` dan salah satu pegawai seed, tanpa baris induk tambahan; SY8 menghitung baris dengan penanda DUMMY atau `ANOMALI-` (Pertanyaan 2).
3. **SY1 untuk ijazah.** Tabel `diploma` lama tidak punya `archive_status`, jadi "keempat status" hanya bisa diperiksa untuk empat jenis lain. Untuk ijazah, SY1 = volume ≥ preset + ada yang diambil dan belum diambil per angkatan (C5). Ini mengikuti skema; bukan perubahan keputusan.
4. **User penulis seed.** `eval_ro` hanya SELECT, jadi `EVAL_SEED_DB_URL` memakai user dengan hak INSERT di `tupoksi_d1` (misalnya root lokal). Penjaga membandingkan host + port + database, bukan user, sehingga URL ini tetap dianggap D1 yang sama dengan `EVAL_OLD_DB_URL`.
5. **Penjaga "target = DB aplikasi"** membaca `DATABASE_URL` dari `.env` hanya untuk dibandingkan; nilainya tidak dicatat. Kalau `DATABASE_URL` kosong, seed berhenti, karena penjaga tidak bisa dibuktikan.
6. **Determinisme lintas mesin.** `random.Random` stabil antar versi Python 3 untuk `random()`, `randrange`, `choice`, dan `getrandbits`. Seed hanya memakai fungsi itu (tidak memakai `sample`/`shuffle` pada set, `uuid4`, `hash()`, atau urutan dict dari DB). Id eksplisit = max(id) + n, jadi dua salinan D1 yang sama menghasilkan id yang sama. Test SY7 di SQLite (Python 3.11 di sini, 3.13 di `.venv` Arya).
7. **SQLite di test vs MySQL di Gate 1.** Integritas FK, panjang kolom (strict mode), dan collation hanya terbukti di MySQL saat langkah 6. Seed memakai panjang kolom dari tabel hasil reflect, dan ada test yang memastikan setiap nilai teks plan ≤ panjang kolom. Seed tidak mengubah `sql_mode` server.
8. **Ukuran transaksi `penuh`** (±22.000 arsip + ±120 pegawai + lampiran ±8.000 berkas). Insert lewat `executemany` per tabel dalam satu transaksi. Lampiran ditulis setelah commit. Kalau penulisan berkas gagal, D1 sudah terisi tetapi berkas kurang; SY5 akan gagal di pemeriksa, dan jalan kembalinya restore D1 + kosongkan folder lampiran (DS1: tidak ada jalan ulang parsial).
9. **`EVAL_STORAGE_ROOT` saat baseline harus diarahkan ke `EVAL_SEED_STORAGE_ROOT`** (DS5). `seed_d1` mencetak pengingat ini; `check_seed_gate` membaca `meta.json` baseline dan menandai SY5 gagal kalau `storage_root` berbeda.
10. **Hash akun seed.** Konstanta argon2 dibuat sekali saat langkah 3 dari sandi acak yang langsung dibuang. Konstanta itu bukan rahasia dan tidak bisa dipakai login (DS7). Tidak ada dependency baru.
11. **D1 tidak boleh dipakai aplikasi lama** (bentrokan 003a). Seed tidak memanggil `create_app()`; test langkah 5 memastikannya, sama seperti test 002b.
