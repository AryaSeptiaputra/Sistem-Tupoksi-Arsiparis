# 001b · Dev · Desain ulang basis data

Status: disetujui 2026-10-04
Dari: docs/rancangan/001a_2026-10-04_dev-desain-ulang-basis-data.md
Kondisi kode: Flask 3.1 + SQLAlchemy 2.0 murni. Skema lama berisi 12 tabel di `app/models/` dengan satu `Base` (`app/core/database.py`), dan dibuat oleh `Base.metadata.create_all` di `create_app()` (`app/__init__.py:80`). Belum ada Alembic, walaupun `alembic==1.17.1` sudah ada di `requirements.txt`. Retensi lama ada di `app/services/disposal.py` (`get_expired_archives`) dan `app/services/retention_scheduler.py`. Hash sandi ada di `app/utils/hash.py` (argon2 atas prehash SHA-256), dan path lampiran di `app/utils/file_helper.py` (simpan `storage/...` di :88, hapus dari `app/static/...` di :40). Project belum punya `errors.py` maupun `setup_logger`. `import app.*` selalu menjalankan `app/__init__.py`, yang membaca `.env` lewat `Settings()` dan membuat engine lama. `.gitignore:18` `test_*.py` ikut mengabaikan semua file test baru di `tests/`. Alat evaluasi dari 002b belum dibangun (0 dari 10). `.venv` memakai Python 3.10.11.

Susunan baru: skema baru, model ORM, dan fungsi domain ditulis di package baru dengan `Base`/`MetaData` sendiri, yaitu `app/db/` dan `app/domain/`. Package ini tidak meng-import `app/models/` lama, karena lima nama tabel (`classification`, `storage_location`, `incoming_letter`, `outgoing_letter`, `diploma`) sama dengan skema lama. ETL ada di `app/etl/`, migrasi di `migrations/` (template aplikasi bisnis), dan titik masuk di `scripts/`. Service, route, dan front-end lama tidak disentuh, dan produksi tetap memakai DB lama sampai cutover (D2).

## Tidak dibangun di rencana ini
- Service, route, schema API, dan front-end baru, termasuk login lewat aplikasi di DB baru. Semuanya masuk rancangan back-end dan front-end (D2).
- Memasang scheduler baru ke APScheduler di `create_app()`, mengganti `DATABASE_URL`, dan cutover. Semuanya rancangan back-end. Scheduler lama tetap berjalan di DB lama.
- Perbaikan `app/utils/file_helper.py` (:40 vs :88). Konvensi path baru (relatif ke `storage/`) dipakai oleh `AttachmentStore` dan ETL. `file_helper.py` lama tetap melayani DB lama yang masih menyimpan awalan `storage/` (Pertanyaan 5).
- Seeder `database/seeders/seed_master.py`, model lama di `app/models/`, dan service lama. Semuanya tidak diubah.
- Isi baris JRA, kode Permendagri per jenis, dan angka retensi. Operator yang mengisinya (001a: skema tidak memuat angka retensi).
- Label golden D2/D3, baris anomali, dump/restore D1, dan menjalankan gate di MySQL sungguhan. Semua perintahnya ditulis di laporan tiap langkah.
- `python-json-logger` / `LOG_FORMAT=json`. Logger hanya `text`, karena belum ada kebutuhan production di rancangan ini.

## Risiko teknis
1. **`.gitignore:18` `test_*.py` mengabaikan semua file test baru** di `tests/` (diperiksa dengan `git check-ignore`), termasuk test 002b. Usulan: ganti menjadi `/test_*.py`, sehingga hanya script ad-hoc di root yang tetap diabaikan, sesuai komentar di atasnya. Paling tepat dikerjakan di 002b langkah 1, yang memang sudah menyentuh `.gitignore`; kalau belum, di 001b langkah 2 (Pertanyaan 6).
2. **`import app.*` ada efek sampingnya.** `app/__init__.py` membaca `.env` dan membuat engine lama. Setiap `conftest.py` di folder test baru memasang env palsu sebelum import, dan test hanya memakai SQLite sementara. Pola ini sama dengan `tests/evaluation/conftest.py` di 002b.
3. **Test lama berbahaya.** `tests/test_pagination.py:30` memanggil `drop_all` ke DB dari `.env`. Test 001b tidak pernah dijalankan dengan `pytest` tanpa path. Test lama tidak diperbaiki di sini.
4. **Default `ON UPDATE CURRENT_TIMESTAMP` hanya ada di MySQL.** Default ini dibuat lewat kompilasi per dialek, jadi SQLite hanya menerima `CURRENT_TIMESTAMP`. M1 di MySQL yang memastikan bentuk akhirnya.
5. **Test SQLite tidak membuktikan perilaku MySQL** (CHECK sejak 8.0.16, collation `utf8mb4_unicode_ci` yang tidak membedakan huruf besar/kecil pada UNIQUE, nama PK selalu `PRIMARY`). Kepastian di MySQL datang dari Gate M1 dan M2 di Dev-A. `pk_%(table_name)s` tidak tampak di MySQL; ini dicatat untuk evaluator M1 002b.
6. **Scheduler menerima `today` sebagai parameter** dan memakai `today.year`, bukan `YEAR(CURDATE())` literal, supaya bisa diuji dengan `tanggal_uji` (kontrak 002b). Rumus dan predikatnya tetap K5. UPDATE multi-tabel dikompilasi SQLAlchemy menjadi `UPDATE archive, classification ... WHERE` di MySQL dan `UPDATE ... FROM` di SQLite ≥ 3.33.
7. **Idempotensi ETL.** Semua `created_at`/`updated_at` ditulis eksplisit: dari baris lama kalau ada, selain itu `etl_date` 00:00. `status_changed_at` baris hasil ETL = NULL, karena waktu perubahannya tidak diketahui. Id baris lama dipertahankan. IJZ = max(id) + 1 dan TANPA-KLAS = max(id) + 2. Id `archive` diberikan berurutan per jenis lalu per id lama.
8. **`alembic upgrade` ke DB yang salah.** Kalau tidak sengaja diarahkan ke DB lama, DDL MySQL langsung di-commit dan sebagian tabel baru terlanjur dibuat di DB produksi. Penjaga di `env.py` menolak DB yang memuat `teacher`/`master_reference`, dan URL diambil dari `NEW_DATABASE_URL`, bukan `DATABASE_URL`.
9. **Menghapus `create_all`** membuat aplikasi lama tidak lagi membuat tabel di DB kosong. DB lama sudah punya tabelnya dan `tests/test_app.py` tidak memakai tabel, jadi aman. Penghapusan ini juga mencegah 12 tabel lama ikut dibuat kalau aplikasi diarahkan ke DB baru.
10. **Panjang kolom baru lebih pendek dari kolom lama.** `teacher.identity_number` 50 → `employee.identity_number` 30, `teacher.full_name` 150 → `app_user.display_name` 100, `master_reference.code` 50 → lookup `code` 30. `master_reference` juga tidak punya UNIQUE (category, code). Di MySQL strict mode, ETL akan gagal di tengah jalan. Usulan: semuanya menjadi pra-cek yang menghentikan ETL dengan pesan jelas (Pertanyaan 2).
11. **Dokumen pegawai tanpa `document_year`.** `archive_year` NOT NULL, dan `/disposal/check` lama memakai `document_year or created_at.year`. Usulan: `archive_year` = YEAR(`created_at`) + dicatat, supaya D4-3 tetap identik (Pertanyaan 1).
12. **Arsip destroyed lama yang masih punya `attachment_path`** melanggar `ck_archive_destroyed_file`. Usulan: path dikosongkan oleh ETL, file tidak dihapus, dan baris dicatat di laporan (Pertanyaan 3).
13. **Ijazah lama tidak punya `archive_status`.** ETL memakai DEFAULT `active`, sesuai 001a.
